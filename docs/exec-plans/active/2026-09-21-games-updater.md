# Standalone games updater

## Context

Roadmap item 4 (`docs/ROADMAP.md:90-98`), the first genuinely *new* user-facing
feature: a small standalone tool that does CRUD (add / update / remove / list)
over `config/installed_games.toml` without running the full installer or
hand-editing the file. Today updating a game list means the whole installer
wizard or a manual TOML edit — jank tolerated only on a dev cabinet.

**Scope of this swing (confirmed with user):** the **validated CRUD core behind a
thin CLI**. The standalone-binary packaging (a PyInstaller `.spec` + build
script) is **greenfield** in this repo — no `.spec` exists and `pyinstaller` is
commented out in `requirements.txt:28` — and is **deferred to its own swing**.
This swing delivers the reusable, validated config-write **spine** that items 2
(installer) and 3 (settings menu) also need, per the ROADMAP's "design that
shared spine once" guidance (`docs/ROADMAP.md:114-115`).

**Anchor: spec** (project default is `outcome`, `.harness/harness.toml`). This is
a **data-losing surface**: a single malformed entry makes `tomllib` reject the
whole file, so every game stops launching, not one. The write-path invariants
(round-trip-verify, atomic replace), the schema-ownership coexistence with the
installer, and the validation contract are decisions with real blast radius that
want a recorded rationale the gate can measure against. `outcome`'s three-bullet
inference would under-serve them. The full gate is forced regardless (data-losing
→ non-overridable, `AGENTS.md` non-negotiables).

### Blind-spot findings (Phase-1 pass over the repo)

- **The ROADMAP's "PyInstaller settings menu" does not exist as source.** There is
  no standalone settings-UI in the repo. The only real add/edit/remove-game code
  is inside the **installer wizard** (tkinter, `install/installer/ui/pages/`), and
  the reusable, GUI-free validation primitives are in
  `install/installer/utils/game_id.py`. So this feature reuses installer
  *primitives*, not a settings-menu build dir — treat the ROADMAP's "settings
  menu" as aspirational, not openable code.
- **Runtime schema** (from `src/arcade_station/launchers/launch_game.py:118-263`,
  generated by `install/installer/config/installation.py:546-571`): top table is
  `[games]`; each entry is keyed by a game ID. **Binary game** = `display_name`,
  `path`, optional `banner`, optional `args` (**string**, never a list —
  `launch_game.py:214-215`). **MAME game** = `display_name`, `rom`, `state`
  (default `"o"`), `banner`. The branch key is **`rom`**: an entry with `rom` is
  MAME, otherwise binary.
- **A malformed entry bricks *every* game.** `load_game_config()`
  (`core_functions.py:644`) calls `tomllib.load`; one bad line rejects the whole
  file and all launches fail (characterized in `tests/test_config_files.py:8-11`;
  `docs/ROADMAP.md:85-86`).
- **The installer owns the schema and rebuilds `[games]` from scratch every run**
  (`installation.py:470-571`: `installed_games = {"games": {}}` at `:475`). It
  loads the existing file only to preserve top-level non-`games` keys and to
  **carry forward** unmanaged per-game keys — currently only `args`
  (`:491-512`). **Coexistence hazard:** a game added *only* by the updater is not
  in the wizard's input, so a later installer reconfigure would rebuild `[games]`
  without it → the game vanishes. This is the shared-ownership constraint
  (`docs/ROADMAP.md:96-98,114-115`) and must be a stated decision, not silently
  resolved (see D6).
- **Core has no TOML *writer*.** `core_functions.py` has readers only
  (`load_toml_config` `:101`, `load_game_config` `:644`). All writing lives in the
  installer. The **safe** writer is `installation._write_toml_manually`
  (`:1233`, via `_write_toml_section` `:1244`, which escapes `\` and `"` at `:1272-1276`) or `tomli_w` (a **real**
  dependency, `requirements.txt:8`). There is a **second, unsafe** hand-rolled
  writer in `install/installer/ui/pages/base_page.py:291-292` that emits
  `f'{key} = "{value}"'` with **no escaping** — a value with a `"` or `\`
  (a Windows path, a URL in `args`) produces invalid TOML. The updater must **not**
  use the `base_page` writer.
- **Reusable primitives** (reuse-before-inventing, `AGENTS.md`): `game_id.py` —
  `generate_game_id(name, existing_ids)` `:5`, `validate_game_id(id)` (regex
  `^[a-z0-9_]+$`) `:32`, `get_display_name(id)` `:45`. Logging:
  `log_message(message, prefix)` (`core_functions.py:818`); prefix vocabulary in
  use includes `MENU`, `GAME`, `GAME_LAUNCH`, `SCRIPT`. Path helpers:
  `convert_path_for_platform` `:75`, `determine_operating_system` `:65`.
- **`load_installed_games()` is a naming trap** (`core_functions.py:229`): it
  loads `pegasus_binaries.toml`, **not** `installed_games.toml`. The correct
  reader is `load_game_config()`.
- **`tomli_w>=1.0.0` is already a real dependency** (`requirements.txt:8`) — no
  new dependency is needed for the write path.

### Decisions taken with the user this session (constrain the register)

- **Anchor: spec** (diverges from the `outcome` default; justified by the
  data-losing surface + schema-ownership constraint above).
- **Scope: validated CRUD core + thin CLI; PyInstaller binary packaging
  deferred** to its own swing.
- **Windows is the primary audience** (Linux is only this dev/CI environment).
  This constrains three design points: (a) the atomic replace uses `os.replace`
  with the temp file in the **same directory** as the target — same-volume is what
  makes the replace atomic on Windows/NTFS; a cross-volume temp is not. (b) Path
  values (`path`, `banner`) are **written exactly as entered** (no slash
  rewriting), which is what the installer's real `tomli_w` write path does — see
  `## Research` R1; this *replaced* the originally approved forward-slash
  normalization after research contradicted it (user re-decided 2026-09-26).
  (c) CI is **Ubuntu-only**, so the Windows-specific failure of `os.replace`
  against a locked/open target (`PermissionError`) is handled in code but recorded
  as **untested-on-Windows** — we do not claim Windows coverage we have not run.

## Proposed acceptance (spec — measurable, gate-checkable)

1. **CRUD works end to end via the CLI.** `python -m arcade_station.tools.games_updater`
   supports `add`, `update`, `remove`, `list` over a target `installed_games.toml`;
   each is demonstrated adding/editing/removing both a **binary** and a **MAME**
   entry, and `list` shows them. Output is exercised in tests, not just asserted.
2. **Every write is round-trip-verified and atomic.** The write path serializes
   with `tomli_w`, re-parses with `tomllib` in memory before touching disk, and
   commits via temp-file + `os.replace`. A test that injects a serialization/
   validation failure proves the **original file is left byte-identical and no
   temp file remains** — the data-losing surface cannot brick all games.
3. **Validation rejects bad input before persisting.** Invalid game ID
   (fails `^[a-z0-9_]+$`), missing required key, empty `path`/`rom`, list-valued
   `args`, duplicate ID on `add`, and `update`/`remove` of a nonexistent ID each
   fail with a clear message and **no file change** (verified by reading back).
4. **Schema matches the installer exactly.** Entries the updater writes carry only
   the D1 keys per type; a written file round-trips through the installer's own
   consumer path shape (rom-or-path branch, args-is-string) — no new keys.
5. **The installer-coexistence limitation is documented, not hidden.** The tool's
   help and this plan state that the installer remains authoritative on
   reconfigure (D6); nothing in this swing silently couples the two owners.
6. **No `skip-worktree` config file is touched, and no `pyproject.toml` /
   new dependency is introduced.** Tests operate on `tmp_path` only; the 12
   personalized files show no edits (verified by reading back, not by trusting an
   empty diff); deps stay `venv` + `requirements*.txt` (`tomli_w` already present).
7. **The menu follows the games table (D9–D14).** Against a copy of a
   realistic `metadata.pegasus.txt`: `add` appends a block in the installer's
   format whose `launch:` ends in the new ID; `update --name` rewrites that
   block's `game:`/`file:` lines in place; `remove` deletes it. Every other block,
   comment and the header are **byte-identical** afterward, and a CRLF file stays
   CRLF. A display name or banner containing a newline is rejected before any
   write.
8. **A failed menu write rolls the TOML back.** A test that makes the menu write
   fail after the TOML write succeeded proves `installed_games.toml` is restored
   to its previous bytes and the command exits non-zero.
9. **Suite stays green and the full gate approves.** The full suite passes (new
   count stated explicitly, not "should pass"); because this is a data-losing
   surface, the change sizes to the **full gate** (adversary + qa + security-brief)
   per `scrutiny.toml`; every required seat is APPROVED at the final sha before
   merge. Never self-merge.

## Design

**Overview.** Two new modules and their tests. A pure, path-parameterized **core
spine** (`games_config.py`) owns loading, validation, the D2 safe-write path, and
the CRUD operations over the in-memory `[games]` table. A **thin CLI**
(`games_updater.py`) is an `argparse` front that resolves the real config path,
calls the spine, and turns exceptions into messages + exit codes. Nothing changes
runtime launch behavior; this only writes the same file the installer writes, more
safely.

**Requirements** (trace to acceptance):
- Add / update / remove / list binary and MAME entries (acc. 1).
- Every persist is round-trip-verified and atomic; the failure path preserves the
  original file (acc. 2).
- Input is validated before any write (acc. 3).
- Written schema matches the installer exactly — D1 keys only (acc. 4).
- The installer-coexistence limitation is documented (acc. 5, D6).
- No `skip-worktree` file touched, no new dep, no `pyproject.toml` (acc. 6).

**Architecture.**

```
CLI: arcade_station.tools.games_updater  (argparse: add|update|remove|list)
  └─ resolves target path (default: config/installed_games.toml) ── only here
     │
     ▼
Core spine: arcade_station.core.common.games_config   (pure, path is a param)
  load_games(path) → dict          validate_entry(id, entry) → raise on bad
  add_game / update_game / remove_game (dict, id, entry) → new dict
  write_games(path, dict): serialize(tomli_w) → reparse(tomllib) → os.replace
```

The spine takes the target path as an argument and never resolves the real config
location itself — only the CLI boundary does that (D7), which is what keeps the
core unit-testable against `tmp_path` and reusable by items 2/3.

**Components & interfaces** (signatures are the contract):
- `class GamesConfigError(Exception)` — base; `class ValidationError(GamesConfigError)`.
- `load_games(path: Path) -> dict` — `tomllib.load` the given file; return the full
  parsed mapping (preserves any top-level non-`games` keys so a write round-trips
  them, mirroring the installer's preservation, `installation.py:477-512`). Missing
  file → an empty `{"games": {}}` skeleton (so `add` to a fresh path works).
- `validate_entry(game_id: str, entry: dict) -> None` — raises `ValidationError`
  with a clear message on: bad ID (reuse `game_id.validate_game_id`), missing
  required key per type, empty `path`/`rom`, non-string `args`, unknown keys
  (guards against D1 drift). MAME iff `"rom"` present.
- `add_game / update_game / remove_game(config: dict, game_id: str, entry: dict|None)
  -> dict` — pure transforms on a copy; `add` rejects a duplicate ID, `update`/
  `remove` require an existing ID. Values are stored exactly as given (R1).
- `write_games(path: Path, config: dict) -> None` — the D2 invariant: serialize
  with `tomli_w.dumps`, **re-parse the text with `tomllib.loads` and assert the
  whole mapping equals** what we intended, write to a temp file in
  `path.parent`, then `os.replace(tmp, path)`. Any failure before `os.replace`
  leaves the original untouched and removes the temp file.

**Data models** (exact on-disk shape, D1):
```toml
[games.street_fighter_iii]      # binary game
display_name = "Street Fighter III"
path = "C:\\Games\\sf3\\sf3.exe"   # stored as entered (R1); tomli_w escapes the backslashes
banner = "C:\\Games\\sf3\\banner.png"   # optional
args = "-fullscreen"                  # optional, always a string
[games.mslug]                   # MAME game (branch key = rom)
display_name = "Metal Slug"
rom = "mslug"
state = "o"                     # default "o"
banner = "C:/mame/art/mslug.png"
```

**Error handling.**
- Validation failures → `ValidationError`; the CLI prints the message via
  stderr and exits non-zero. No file written. (Successful changes are
  recorded with `log_message(msg, "GAME")`.)
- `write_games` failures before `os.replace` (serialize error, round-trip
  mismatch) → temp removed, original intact, `GamesConfigError` raised.
- **Windows-specific:** `os.replace` against a target open in another process
  raises `PermissionError` on Windows; caught and reported as "config is in use,
  close arcade_station and retry" rather than a stack trace. Recorded as
  **untested-on-Windows** (Ubuntu CI cannot exercise the Windows lock semantics).

**Testing strategy.** Unit tests on the spine against `tmp_path` (D7 — never the
real config). Cover: add/update/remove/list for both game types; validation
rejections (bad ID, missing key, empty path/rom, list-valued `args`, dup ID,
missing ID); **atomicity** by monkeypatching `tomli_w.dumps` (or the reparse) to
raise and asserting the original file is byte-identical and no temp file remains;
Windows backslash paths round-trip unchanged. Mirrors `tests/test_installer_toml_writer.py` and
`tests/test_config_files.py` fixture style. Full suite must stay green (new count
stated at gate, not "should pass"). Backslash round-tripping is pure
serialization so it is proven on Ubuntu; `os.replace` Windows-lock behavior is
not (recorded, not claimed).

### Design addendum — menu sync (D9–D14)

- **Shared atomic writer.** `games_config.atomic_write_bytes(path, data)` is
  factored out of `write_games` (temp file in the target's directory, fsync, copy
  mode, `os.replace`, temp removed on failure, `PermissionError` →
  `GamesConfigError`). `write_games` and the menu writer both call it, so there is
  one implementation of the D2 guarantee.
- **New module `src/arcade_station/core/common/pegasus_menu.py`** (pure,
  path-parameterized, like the spine):
  - `load_menu(path) -> MenuDocument` — reads UTF-8 bytes, records the newline
    style (`\r\n` if present, else `\n`), splits into header lines and blocks
    per D9. Each block keeps its original lines verbatim plus its parsed game ID
    (or `None` when opaque). Missing file → the installer header.
  - `upsert_game_block(menu, game_id, entry) -> MenuDocument` and
    `remove_game_blocks(menu, game_id) -> (MenuDocument, int)` — D10, returning
    new documents.
  - `render(menu) -> bytes` — joins untouched blocks from their original lines,
    so they are byte-identical; new or rewritten lines use the file's newline.
  - `write_menu(path, menu)` — `render`, then `atomic_write_bytes`.
- **CLI orchestration (D12).** Each command loads both files, builds both new
  documents, writes the TOML, then the menu; on a menu failure it restores the
  TOML's original bytes with `atomic_write_bytes` and exits 1. `--menu-file`
  defaults to `<repo>/src/pegasus-fe/config/metafiles/metadata.pegasus.txt` (a
  `skip-worktree` file; tests never touch it). On success it prints a restart
  reminder (D14).
- **Validation (D13).** `validate_entry` also rejects `\r`/`\n` in
  `display_name` and `banner`.

| **D11** | **New block format** | Mirror `_generate_pegasus_metadata` (`installation.py:806-958`) exactly: `game: <title>`, `file: not\using\files\to\launch\games\<title>`, `sortBy: <letter>`, the three-line quoted `launch:` value with the installer's trailing spaces, then the asset line. The python and launcher strings are **copied from an existing block** (they are identical across blocks on a cabinet); fallback is the installer formula with the repo root as `install_path` (`.venv/Scripts/pythonw.exe` on Windows, matching `launch_arcade_station.bat:45-48`). Title = `display_name`, else `get_display_name(id)`. Asset: binary → banner with `\` → `/`, line omitted if empty; MAME → same, defaulting to `../../../../assets/images/banners/arcade_station.png`. `sortBy` = the letter after the highest single-letter `sortBy` in the file (new games land at the end of the menu), `a` if none. The installer's MAME `install_path` → `../..` relativization is **not** copied (an absolute path works and that rewrite looks wrong). | A new block is indistinguishable from an installer-written one on the same cabinet. Copying launch strings from the file itself is correct by construction; the formula only covers an empty menu. |
| **D12** | **Two-file consistency** | Validate and build **both** documents in memory before writing either. Write `installed_games.toml` first, then the menu file, each with the D2 atomic replace. If the menu write fails, **restore the previous TOML bytes** through the same atomic path and report the error. A crash *between* the two writes can still leave them out of step; that is documented, not claimed away. | Two files cannot be replaced atomically together. Rollback gives all-or-nothing for every failure short of a process kill. |
| **D13** | **Menu injection safety** | Values that reach the menu (`display_name`, `banner`) must be **single-line** — reject `\r`/`\n` in `validate_entry`. IDs are already `^[a-z0-9_]+$`. | The metadata format is line-based: a newline plus `game:` in a display name would inject a menu entry (or break the file). TOML would happily store it, so the TOML round-trip does not catch this. |
| **D14** | **Encoding, line endings, missing file, restart** | Read and write the menu file as UTF-8, **preserving its existing line-ending style** (the installer writes it in text mode, so CRLF on Windows); new blocks use the same ending. A missing file is created with the installer's header. After a change, the CLI tells the user to restart Arcade Station, since Pegasus reads metadata at start. `--menu-file` overrides the default path. | Windows-primary: a mixed-ending file is the likeliest real-world corruption. Pegasus picks up edits only on restart; saying so avoids a "didn't work" report. |

## Research

Findings from the Step-1 read of the code being reused; each changed a decision
or an implementation detail.

- **R1 — the installer does not normalize path slashes on a real cabinet.**
  `InstallationManager._write_toml` (`install/installer/config/installation.py:1217-1230`)
  imports `tomli_w` and calls `tomli_w.dump` — no slash rewriting. The
  `\ → /` rewrite (`:1269-1271`) lives only in `_write_toml_section`, reached via
  `_write_toml_manually` on `ImportError`. `tomli_w>=1.0.0` is in
  `requirements.txt:8` (1.2.0 in this venv), so cabinets take the `tomli_w`
  path. Runtime consumes `path`/`banner` via `os.path.exists` / `os.path.dirname`
  / PowerShell `Start-Process` (`launch_game.py:153-158,212-263`), which accept
  either slash style on Windows. **Contradicted approved design point (b);
  surfaced to the user, who chose to preserve paths as entered.**
- **R2 — `display_name` is not universally present.** The installer writes the
  `itgmania` entry as `{path, banner}` only (`installation.py:526-539`). So
  `display_name` cannot be a required key in validation: required is `path`
  (binary) or `rom` (MAME). The CLI still requires a name on `add`, because that
  is what the ID is generated from.
- **R3 — a game entry can be a bare string.** `launch_game.py:214` handles
  `game_config` that is not a dict as a path. The installer never writes that
  shape, so any such entry was hand-edited. The updater preserves the data of
  every untouched entry (the whole parsed mapping round-trips; comments and
  formatting in `installed_games.toml` are not kept, exactly as with the
  installer's own `tomli_w` write — disclosed in `--help`), `list` shows them, and
  `update` refuses them with a clear message rather than silently rewriting a
  user's hand-edit. `remove` works on them.
- **R4 — reusing `game_id.py` from runtime code.** The repo runs in place: the
  launcher and installer both run from the clone (`install_logic.ps1:61-67,108`,
  venv at `install\.venv`), so `install/installer/utils/game_id.py` is on disk
  on every cabinet. `installer/__init__.py` imports only `platform`/`os` (no
  tkinter), so importing `installer.utils.game_id` is cheap. The spine inserts
  `<repo>/install` onto `sys.path`, which is the convention every runtime module
  already follows for `src` (e.g. `launch_game.py:24`). No duplicated regex.
- **R5 — the Pegasus menu is generated from `metadata.pegasus.txt`, not from
  `installed_games.toml`.** `_generate_pegasus_metadata`
  (`installation.py:806-958`, called at `:300`) rebuilds the whole file from the
  wizard's `binary_games` / `mame_games` / `itgmania` input on every run. Each
  block's `launch:` runs `launch_game.py <id>`; `installed_games.toml` only
  resolves how that ID launches. **Changed the scope** (D9–D14).
- **R6 — Pegasus metadata syntax** (https://pegasus-frontend.org/docs/user-guide/meta-files/):
  `name: value` entries; "Values can span multiple lines, but additional lines
  have to start with at least one space or tab"; lines starting with `#` and
  empty lines are ignored; "All entries belong to the last defined `collection`
  or `game` entry". `sortBy` is "An alternate title that should be used for
  sorting"; without it the title is used. This is why D13 rejects newlines and
  why D9 bounds blocks at column-0 `game:` / `collection:` lines.
- **R7 — runtime venv.** `launch_arcade_station.bat:45-48` runs from
  `<repo>\.venv\Scripts`, which matches the installer's
  `install_path/.venv/Scripts/pythonw.exe` launch string (the wizard's own
  `install\.venv` is separate), so the D11 fallback formula is correct.

## Deviations

- **No `tools/__init__.py`.** The design listed one, but nothing under
  `src/arcade_station` has an `__init__.py` (all namespace packages), so
  `tools/` follows that convention. No interface change.
- **Invocation form (disclosed; the approved form still works).** D4 named
  `python -m arcade_station.tools.games_updater`. The project is not
  pip-installed, so that form works only with `src` on the path (e.g. run from
  `src/`); from the repo root it fails with `No module named 'arcade_station'`
  (verified). The module therefore also inserts `src` onto `sys.path` like every
  other runtime entry point, and its documented usage is the script form
  `python src/arcade_station/tools/games_updater.py …` from the repo root — the
  same way `launch_arcade_station.bat:66` runs `start_frontend_apps.py`. Both
  forms were run and work.
- **Comment ownership in the menu file (found by a failing test).** As first
  built, a `#` comment line above a block was attributed to the block *before*
  it, so removing that earlier game deleted a comment describing the next one.
  Fixed: comments directly above a `game:` line belong to that game; separating
  blank lines stay with the block above. Pinned by
  `test_opaque_blocks_are_never_removed` and
  `test_comment_above_a_block_belongs_to_that_block`.
- **Appending after a file with no final newline.** The previous last line
  gains the missing line ending and a blank separator line before the new
  block; all existing bytes remain an exact prefix of the output (pinned by
  `test_new_binary_block_matches_installer_format`).
